# AGENTS.md — инструкция для любой нейросети и любого разработчика

Ты получил ссылку на этот репозиторий. Это **учебная ОС для x86_64 (UEFI, свой загрузчик MigaBoot)**.
Цель проекта: довести её до **юзабельной ОС**: загрузка на реальном железе, процессы в user mode,
файловая система на диске, ввод (клавиатура/мышь/USB), GUI-приложения как отдельные программы, сеть.

Весь план лежит в `ROADMAP.md` и разбит на **микро-шаги** (ID вида `3.2.4`). Твоя работа: **взять один свободный шаг, выполнить только его, записать в журнал что и когда изменено и перевести шаг в `REVIEW`.** Тестирует и ставит `DONE` владелец репозитория.

## 0. Роли: кто что делает (главное правило проекта)

| Кто | Что делает | Чего НЕ делает |
|---|---|---|
| **Исполнитель** (нейросеть) | читает код, пишет и правит код и документы, ведёт журнал, чинит ошибки по присланным логам | **не компилирует, не запускает QEMU, не гоняет тесты и не утверждает, что что-то собралось или работает** |
| **Владелец репозитория** | **один компилирует** (`make`) и **один тестирует** (QEMU, реальное железо), присылает исполнителю вывод ошибок и логи, ставит `DONE` | не обязан угадывать, что сделал исполнитель: всё описано в журнале |

Из этого следует:
- Весь код пишется **без возможности проверить его сборкой**, поэтому нужна повышенная аккуратность (раздел 6.1).
- Любая фраза «собирается», «компилируется», «работает», «тесты проходят» от исполнителя **запрещена**. Допустимо только: «написано, не компилировалось».
- Ошибки сборки и тестов приходят от владельца (вставленный текст вывода `make`, serial-лог, описание экрана). Исполнитель чинит их по этим данным.

## 1. Что сделать в самом начале (обязательно)

1. Прочитай `README.md`, `ROADMAP.md`, `docs/LOG.md`.
2. Если есть `docs/ABI.md` или `docs/CONTRACTS.md`, прочитай их.
3. Посмотри реальный код в тех путях, которые указаны в твоей задаче. **README может отставать от кода.**
   Если они расходятся, верь коду и запиши расхождение в `docs/LOG.md`.
4. Только после этого выбирай задачу.
5. Узнай точную текущую дату (см. раздел 7), она понадобится для журнала.

## 2. Как выбрать шаг

- Если пользователь назвал ID (шаг `3.2.4`, задачу `3.2` или этап), работай с ним. Для задачи без шага бери её первый свободный шаг.
- Иначе иди по `ROADMAP.md` сверху вниз и бери **первый шаг со статусом `TODO`**, у которого:
  1. предыдущий шаг той же задачи в статусе `REVIEW` или `DONE`;
  2. все задачи из строки «зависит от» этой задачи полностью в статусах `REVIEW` или `DONE`.
- Не бери шаги со статусами `WIP`, `REVIEW`, `BLOCKED`, `DONE`.
- Шаги разных независимых задач можно делать параллельно: над ними могут работать разные исполнители.

## 2.1. Правило малых шагов («по чуть-чуть»)

ОС растёт маленькими безопасными порциями. Поэтому:

1. **За один сеанс делай один шаг.** Два шага допустимы, только если оба тривиальны и идут подряд в одной задаче.
2. **Размер шага:** примерно до 300 изменённых строк и до 5 файлов. Если шаг не помещается, **раздели его** в `ROADMAP.md` на `N.N.Na`, `N.N.Nb`, сделай только первую часть и запиши это в журнал.
3. **Не опережай план.** Не делай «заодно» соседние шаги, не рефакторь чужой код, не добавляй возможности, которых нет в шаге.
4. **Не ломай то, что работало.** Шаг не должен ломать сборку и загрузку (проверит владелец), поэтому пиши аккуратно и консервативно.
   Новый код подключай так, чтобы его можно было отключить (отдельные файлы, команда kshell для запуска, флаг), пока он не проверен владельцем.
5. **Нашёл баг или недостающее?** Не чини вне шага. Добавь новый шаг в конец нужной задачи в `ROADMAP.md` (следующий номер) и упомяни его в журнале.
6. **Один шаг = один коммит** (или короткая серия), сообщение `[3.2.4] описание`.
7. Тестирует владелец на отметках `🏁` у задачи, когда все её шаги в `REVIEW`. Для каждого шага всё равно пиши инструкцию «как собрать и проверить» для владельца, даже если это просто «выполни `make` и пришли вывод».

## 3. Как занять задачу

Поменяй в `ROADMAP.md` статус своей строки с `TODO` на `WIP` и закоммить это **отдельным маленьким коммитом первым**:

```
[3.2.4] claim: WIP
```

Работай в ветке `step/<ID>` (например `step/3.2.4`). Если у тебя нет доступа к git, см. раздел 8.

## 4. Правила кода

- Инструменты: только `gcc` + `binutils` + `make` + `python3` для скриптов в `tools/`. **Никаких внешних библиотек в ядре.**
- Код должен быть написан так, чтобы собираться **без предупреждений** (проверит владелец). Если в `Makefile` нет `-Wall -Wextra`, не добавляй их без задачи на это.
- **Граница ядро ↔ драйверы:** драйверы в `drivers/` видят только `include/miga/`. Не подключай `kernel/include` из драйверов.
  Всё, что драйверу нужно от ядра, объявляется в `include/miga/*.h`.
- Драйвер регистрируется макросом `MIGA_DRIVER(...)`, и вызывать его напрямую нельзя.
- Новая команда kshell: функция `c_xxx(int argc, char **argv)` и строка в `table[]` в `kernel/core/kcmds.c`.
- Новое GUI-приложение: `kernel/gui/apps/` и строка в `apps[]` в `kernel/gui/server.c`.
- Следуй стилю соседних файлов (отступы, именование, язык комментариев).
- Меняй **только пути, указанные в твоей задаче**. Нужно выйти за них? Допиши причину в `docs/LOG.md` и сделай минимальную правку.
- **Замороженные контракты** (`include/miga/*.h`, `docs/ABI.md`): меняй их только если твоя задача прямо это требует,
  и только обратно совместимо (добавлять, а не ломать).

## 5. Статусы и кто их ставит

```
TODO  →  WIP  →  REVIEW  →  DONE
                    ↓
                  TODO / BLOCKED  (если тест владельца не прошёл или есть блокер)
```

| Статус | Значение | Кто ставит |
|---|---|---|
| `TODO` | свободна | — |
| `WIP` | исполнитель работает | исполнитель |
| `REVIEW` | код написан, **не компилировался**, ждёт сборки и теста владельцем | исполнитель |
| `DONE` | владелец проверил (обычно на отметке 🏁 всей задачи) и подтвердил | **только владелец репо** |
| `BLOCKED` | есть блокер, причина в `docs/LOG.md` | исполнитель |

**Исполнитель никогда не ставит `DONE`.** Тестирует владелец репозитория сам (запуск в QEMU и на железе).
Задача, у которой зависимости в статусе `REVIEW` или `DONE`, считается доступной. Если позже тест `REVIEW`-задачи провалится,
зависимые задачи нужно перепроверить.

## 6. Definition of Done для исполнителя (когда можно ставить `REVIEW`)

- [ ] Выполнен критерий готовности шага (после стрелки `→` в столбце «Шаг» в `ROADMAP.md`) и **ничего сверх него**.
- [ ] Выполнена **ручная самопроверка** кода (раздел 6.1), её результат кратко описан в журнале.
- [ ] Обновлена документация (`README.md` или `docs/*`), если изменилось поведение или структура.
- [ ] В `docs/LOG.md` есть полная запись (формат ниже), включая **команды сборки и теста для владельца**.
- [ ] Статус шага в `ROADMAP.md` → `REVIEW`.

Исполнитель **не запускает** `make`, `make check`, `make test`, QEMU и не пишет, что они пройдены. Это делает владелец.

## 6.1. Как писать код, который нельзя скомпилировать самому

Перед тем как отдать шаг, проверь глазами:
- Все `#include` существуют в репозитории (сверься с реальными путями, а не по памяти). Драйверы не подключают `kernel/include`.
- Все вызываемые функции и структуры **реально существуют** в коде с такими именами и сигнатурами (открой файл и проверь). Не выдумывай API.
- Типы и форматы: `uint64_t` против `size_t`, `printf`-подобные форматы ядра (`kprintf`) соответствуют аргументам.
- Каждая новая функция объявлена до использования или в заголовке; нет неиспользуемых переменных и параметров (предупреждения).
- Новые `.c` файлы попадают в сборку автоматически? Если нет, дополни `Makefile` (в README сказано, что `kernel/gui/` и `drivers/` подхватываются сами; проверь по `Makefile`).
- Ассемблер: синтаксис совпадает с остальными `.S` файлами (AT&T или Intel), секции и выравнивание как в соседних файлах.
- Нет UB: размеры массивов, приведения указателей, выравнивание структур для железа (`__attribute__((packed))` там, где нужно).
- Опиши в журнале, **что ты проверил глазами и что сомнительно**, чтобы владелец знал, куда смотреть при ошибке сборки.

## 6.2. Цикл «сборка → ошибка → исправление»

1. Исполнитель сдаёт шаг в `REVIEW`, в журнале написано, как собрать (`make`) и что проверить.
2. Владелец собирает и тестирует. Если всё хорошо, он пишет результат в журнал и (на отметке 🏁) ставит `DONE`.
3. Если сборка или тест упали, владелец присылает исполнителю **полный текст ошибки или лога** и название шага.
4. Исполнитель исправляет **только это** и добавляет в журнал новую запись: `[ID] fix: <что упало>`, со ссылкой на присланный вывод, перечнем правок по файлам и указанием, что **исправление снова не компилировалось**.
5. Шаг возвращается в `REVIEW`. Цикл повторяется до успеха.

Если вывод ошибки неполный или непонятный, исполнитель просит нужное (`make V=1`, полный лог, `-serial stdio`), а не гадает.

## 7. Честность — главное правило

- **Никогда не пиши «собирается», «работает», «протестировано».** Исполнитель ничего не компилирует и не запускает. Пиши: «написано, не компилировалось, не запускалось».
- Не выдумывай результаты тестов, адреса, логи и API. Если чего-то не знаешь, посмотри в код или спроси владельца.
- Заглушки допустимы только явно помеченные `TODO(<ID>)` и перечисленные в записи лога.
- **Не выдумывай дату.** Узнай её командой `date '+%Y-%m-%d %H:%M %Z'` (или `git log -1 --format=%cd --date=iso`).
  Если у тебя нет ни командной строки, ни системной даты, **спроси дату у владельца** или напиши `дата: уточнить`.
  Угадывать дату по памяти нельзя.

## 7.1. Журнал: когда и что изменено

После **каждой** задачи (и после каждого значимого шага внутри большой задачи) добавляй запись в **конец** `docs/LOG.md`.
Записи не редактируются и не удаляются: исправление оформляется новой записью.

Формат записи (все поля обязательны):

```
## [ID] Название задачи
- Дата и время: ГГГГ-ММ-ДД ЧЧ:ММ (часовой пояс)
- Исполнитель: модель или человек (например, Claude / GPT / Gemini / имя)
- Статус после записи: WIP | REVIEW | BLOCKED
- Что изменено (по файлам):
  - `путь/к/файлу.c` — что именно: добавлена функция X, удалён Y, исправлена ошибка Z
  - `путь/к/другому.h` — ...
- Зачем: одна-две фразы, почему сделано так
- Что не сделано / заглушки: список или «нет»
- Самопроверка (что проверено глазами, что сомнительно): ...
- Как собрать и проверить (для владельца):
  1. команды (`make`, затем `make run` ...)
  2. что должно появиться в выводе / на экране при успехе
  3. что считать провалом и какой вывод прислать исполнителю
- Результат сборки владельца: _ожидает_ (владелец: собралось / ошибки + вывод, дата)
- Результат теста владельца: _ожидает_ (владелец: прошёл / не прошёл + описание, дата)
```

Поле «Результат теста владельца» заполняет **владелец** (дата + «прошёл» / «не прошёл» + вывод ошибки).
После «прошёл» владелец ставит `DONE` в `ROADMAP.md`. После «не прошёл» исполнитель берёт задачу заново:
статус возвращается в `TODO` (или `WIP`), а в логе появляется новая запись, ссылающаяся на провал.

Правила для содержимого записи:
- Перечисляй **каждый** изменённый, созданный и удалённый файл. Формулировки вида «разные правки» недопустимы.
- Если менялся публичный контракт (`include/miga/*.h`, `docs/ABI.md`), выдели это отдельной строкой `КОНТРАКТ:`.
- Если найдено расхождение README и кода, добавь строку `Расхождение:`.

## 7.2. Коммиты и завершение

1. Коммиты: `[ID шага] краткое описание`. Один логический шаг = один коммит. Дату в коммит писать не нужно: её ставит git.
2. Запись в `docs/LOG.md` коммитится вместе с кодом задачи или сразу после него.
3. Затем PR из `step/<ID>` в `main` (или передача файлов владельцу, см. раздел 8).
4. Если застрял: статус `BLOCKED`, в `docs/LOG.md` напиши, что мешает и что ты уже пробовал. Это лучше, чем молча бросить.

## 8. Если у тебя нет доступа к git (ты чат-ассистент)

- Скажи пользователю, какой шаг берёшь (ID и название).
- Выдай **полные содержимые файлов** с путями (не диффы «вставь сюда»), по одному блоку на файл.
- В конце перечисли команды для сборки и проверки владельцем (`make`, `make run`) и что ожидать в выводе. Напомни: если сборка упадёт, пусть пришлёт полный текст ошибки.
- Выдай готовую запись для `docs/LOG.md` (в заголовке — ID шага; статус кода: «не компилировалось») (с датой и временем, списком изменённых файлов и инструкцией для тестирования)
  и готовую правку статуса в `ROADMAP.md` (`REVIEW`). Если не знаешь дату, спроси её у пользователя до того, как писать запись.
- Если шаг слишком большой для одного ответа, раздели его на подшаги (`N.N.Na`, `N.N.Nb`), сделай первый и честно скажи, что осталось.

## 9. Быстрая шпаргалка

```
sudo apt install build-essential qemu-system-x86 ovmf mtools
make            # сборка → build/esp/
make run        # QEMU + OVMF, serial в терминал
make disk       # build/miga.img (FAT32)
make check      # неопределённые символы libdrivers.a = реальный API драйверов
```

Загрузка: UEFI → `\EFI\BOOT\BOOTX64.EFI` (MigaBoot) → читает `\EFI\MIGA\kernel.elf` → `boot_info` → `ExitBootServices` → `_start` ядра (`RDI = boot_info*`).
